## چرا Python گلوگاه نمی‌شود

حجم کار را اندازه بگیریم:

- **جهان نمادها:** حدود ۱٬۰۰۰ تا ۲٬۰۰۰ نماد (سهام، حق‌تقدم، صندوق).
- **داده لحظه‌ای:** دیده‌بان بازار TSETMC همه نمادها را در یک پاسخ برمی‌گرداند؛ هر ۱۰ ثانیه ≈ ۰.۱ درخواست در ثانیه و حدود ۷۰۰ ردیف در ثانیه نوشتن. برای TimescaleDB ناچیز است.
- **آموزش مدل:** ۲٬۰۰۰ نماد × ۲٬۵۰۰ روز ≈ ۵ میلیون ردیف × ~۲۰۰ ویژگی. LightGBM (هسته C++) روی یک سرور ۸ هسته‌ای در چند دقیقه.
- **محاسبه ویژگی:** Polars (هسته Rust، چندنخی، برداری) — حلقه Python روی ردیف‌ها **ممنوع**.

گلوگاه واقعی **محدودیت نرخ منابع داده و پایداری آن‌ها** است، نه زبان. Python بیشترین اکوسیستم مالی و ML را دارد و یک زبان واحد برای داده، مدل و API پیچیدگی تیم را کم می‌کند.

## راه فرار (تعریف‌شده، فعلاً پیاده نمی‌شود)

اگر ورود داده لحظه‌ای عمق سفارش برای همه نمادها لازم شد و تأخیر p95 از ۲ ثانیه بیشتر شد، فقط سرویس `ingest-realtime` با **Go** بازنویسی می‌شود. قرارداد بین سرویس‌ها (جداول DB و پیام‌های Redis Streams) از الان ثابت است تا این جایگزینی بدون تغییر بقیه ممکن باشد.

## گزینه‌های ردشده

- **فقط TypeScript/Node:** اکوسیستم ML و آماری ضعیف.
- **Go یا Rust برای همه:** کندی توسعه مدل و تحلیل؛ سود کارایی لازم نیست.
- **MongoDB/ClickHouse:** داده رابطه‌ای و سری زمانی هر دو را PostgreSQL+Timescale پوشش می‌دهد؛ یک DB کمتر.
- **Prefect/Airflow:** برای این مقیاس سنگین‌تر از Celery Beat.
